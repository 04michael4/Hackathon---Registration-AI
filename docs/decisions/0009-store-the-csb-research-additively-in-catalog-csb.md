# ADR-0009: Store the Computer Science and Business (CSB) research additively in `catalog_csb`

- **Status:** Proposed. Implemented in [data/csb-research](../../data/csb-research/README.md) and verified (2026-10-18) on isolated copies of the unified database, the last one a fresh copy of the live team database taken that day. Not installed in any shared database, not pushed. It changes no shared interface. The owner of `catalog_research` (Account 1) has not reviewed it yet.
- **Scope:** a new additive schema `catalog_csb`. No change to `catalog_research`, `catalog_serving`, `professor_ratings`, `catalog_promoted`, `catalog_live`, `catalog_api`, `banner_evidence`, `cse007_snapshot`, the backend, the engine or the frontend.
- **Number:** 0009 is the next free number: no other branch, remote or worktree of the repository holds an ADR numbered 0009 or higher (checked 2026-10-18 against all local and remote branches and all worktrees). Renumber if another ADR lands first.

## Problem
The CSB degree needs courses the unified database does not hold (business, accounting, economics, natural science and CSB-subject courses), with their Spring 2027 sections, Class Details, linked lab/recitation structure, instructors, and the degree's own structure (136 credits, alternatives, categories, a 9-credit professional-elective rule that has no published approved list, and suggested natural-science sequences). The existing `catalog_research` importers cannot take it without harming data another person is working on:

- `import_noncse_term` replaces **every** grid-staged offering of the term, and `import_degree_programs` clears the global cross-list and exclusion tables. Running either with CSB data would delete or overwrite the 243 existing sections' neighbours, and rerunning Account 1's importer would in turn delete CSB rows if they shared its `data_source`.
- Its CHECK constraints (`data_source`, `catalog_course.catalog_status = PROGRAM_TABLE_ONLY`, `prerequisite_status = NOT_COLLECTED`) cannot hold Class-Details-inspected sections or catalog prerequisites; widening them changes a schema that is under active work.
- Instructor names read from an authenticated Banner session must stay local-only; `catalog_research` deliberately never imports names.

## Decision
1. **A separate schema, built on the same conventions.** `catalog_csb` uses `term_code`, `SUBJ-NNN` ids, CRN keys, component types, evidence levels, a hashed append-only `import_run`, verbatim-grid cross-check views (`grid_mismatch`, `link_status_mismatch`), owner/reader roles, `install.sql`, `verify_structure.sql`, a transactional importer with `--dry-run`, and mutation-checked validation. It has **no foreign key to, and no dependency on, anything outside itself** by default, and nothing outside depends on it; `verify_structure.sql` asserts this and `rollback.sql` re-checks it before it drops anything. The only coupling is **optional and separate**: five coverage views (`install_coverage_views.sql`) that *read* four `catalog_research` objects. They are not part of the default install because they make an `ALTER`/`DROP` of those objects by the owner of `catalog_research` fail (tested), and a `DROP ... CASCADE` there would silently drop them (never data).
2. **The importer replaces only its own schema's data.** `catalog_csb.import_csb` truncates and reloads catalog_csb in one transaction and refuses to finish if any normalized row disagrees with the verbatim grid row, or a link status disagrees with the Linked Sections panels. It also refuses a CRN that already exists in `catalog_research`. Rerunning gives identical content, and the content fingerprint does not depend on the database collation (a defect found on 2026-10-18 when the first copy, `en_US.UTF-8`, and the team database, `C.UTF-8`, gave different hashes for identical data).
3. **Stored is not approved is not registrable.** The schema has no approval, promotion, serving or Registrar-certification column (asserted). Nothing here is read by the backend or by `catalog_serving`.
4. **Nothing is inferred.** A link between sections is `CONFIRMED_BOTH_SIDES` only when each side's panel lists the other; a Linked Sections panel lists *options*, and whether registering for one is mandatory is not stated by the panel (`requirement_basis`); credits are the results grid's numbers, counted once per lecture, with Class Details' differing figure (the bundled total shown on a linked lab) flagged, not trusted; an unrecognized prerequisite or restriction stays words (`TEXT_ONLY`).
5. **Sources that disagree stay side by side.** The catalog (primary) and Banner prerequisite statements are compared per course (`prerequisite_comparison`) and both kept; the catalog's 136-credit degree is kept next to the program website's and the CSE department page's differing statements (`source_conflict`).
6. **Approval is never assumed.** Only the 2026-27 catalog's own CSE elective list is `CATALOG_LISTED`. Every CSB professional-elective candidate (CSB-prefixed courses, track examples, the CSE list used as a professional elective) is `APPROVAL_NOT_VERIFIED`, enforced by a CHECK and a second check in `program_problem`.
7. **Banner-derived rows are local-only.** Their `source` row says `NOT_VERIFIED_LOCAL_ONLY` (a CHECK ties authenticated Banner to that status). The import payload, raw captures, instructor names, CRNs and catalog prose live outside the repository (`~/.registration-csb/`); the committed tests use a synthetic dataset, and `check_no_restricted_data.py` scans what is about to be committed for real CRNs, instructor names, copied Banner/catalog text, credentials and home-directory paths.

## How the backend can eventually consume validated CSB courses
**Principle: there is one gate and it stays where it is.** A course reaches the application only through `catalog_research` → `offering_tier` → `catalog_serving.served_offering` and its conditions ([ADR-0007](0007-serve-researched-courses-with-their-conditions.md)), or through the approvals of [ADR-0003](0003-promote-evidence-through-approvals-into-catalog-live.md). `catalog_csb` gets **no** path of its own: not `DB_CATALOG_SCHEMA=catalog_csb`, not a `UNION` inside a serving view, not a grant to the application role. A bypass would split the safeguards in two places that drift apart. Concretely it would skip: the BLOCKED rules in `offering_tier` (evidence or Class Details mismatch, a lab or recitation not linked to exactly one lecture, an unsupported section type, an undecided topic identity); the condition rendering of `course_condition`, which only knows the rule kinds `CLASS_STANDING`, `LEVEL`, `COLLEGE`, `MAJOR`, `DEPARTMENT_APPROVAL`, `PREREQUISITE` and `COREQUISITE`, so CSB's `DEGREE` restrictions (98 sections) would be silently dropped and a course would look less restricted than Banner says; and the single CRN namespace (`catalog_research.section` is keyed by `(term_code, crn)`; a second source could show one CRN twice).

**Path (each stage needs an approval; none is implemented):**
1. *Done: store.* `catalog_csb` holds the research; the importer guards against CRN collisions; nothing is served.
2. *Agree the route with the owner of `catalog_research`.* The recommended route is to feed CSB sections into `catalog_research` through **its own pipeline**, as grid-staged offerings with Class Details inspected, because they are the same kind of evidence (an authenticated Banner grid plus Class Details) and because `import_noncse_term` replaces all grid-staged offerings of the term: CSB rows must be part of that one dataset or the next non-CSE import deletes them. The work is an adapter that reads `catalog_csb` (read-only) and writes the pipeline's local-only export and capture files. `catalog_csb` is not edited.
3. *Vocabulary migration in `catalog_research` (its owner's migration).* Add the rule kinds `DEGREE` (and `COHORT`, none stored yet) and the prerequisite "minimum grade shown" (Banner prints `TR`; its meaning is unresolved), and render them in `course_condition` as `UNVERIFIED` conditions. Decide the two open modelling questions that ADR-0008 already lists: a lab or recitation shared by several lectures, and a lab-only course.
4. *`catalog_serving` serves what passes its existing gate.* Measured on the isolated copy with the current gate's own conditions, **38 of the 43 offerings (165 of the 213 sections) would be eligible** once step 3 exists. Five stay BLOCKED for the same reasons as CHM 030 and PHY 012 today: CHM 031, FIN 125 and PHY 021 (their labs or recitations, 35 sections, are listed by two lectures each), EES 022 (lab-only, 5 sections), and the independent-study offering (variable credits, an Independent Study section type that needs a team-policy decision as for CSE 217). 12 of the 38 carry a `DEGREE` rule.
5. *Separate decisions, not part of this route:* the degree structure into `catalog_research`'s program tables (`import_degree_programs` clears global tables, so it must be coordinated, and the professional-elective list is unverified); CSB instructors into `professor_ratings` (16 of the 78 names already exist there; the other 62 would be new; [ADR-0006](0006-store-professor-ratings-separately-from-the-catalog.md) point 2 applies); catalog descriptions (copyrighted prose, not committed).

**Identity invariants to hold at every stage** (checked on 2026-10-18 against the fresh copy): no CSB CRN equals a CRN in `catalog_research`, `catalog_serving`, `banner_evidence`, `cse007_snapshot` or `professor_ratings` (0 collisions); no CSB offering equals a `catalog_research` offering (0 of 43); the 36 catalog identities that exist in both are references (titles agree wherever both have one: 12 equal, 28 absent in `catalog_research`, 0 different); `course_id` is `SUBJ-NNN` in both; Banner prerequisite expressions use the same `{"op","args"}` / `{"course"}` JSON (CSB lacks only the `concurrent` flag, which Banner's panel does not give).

## Rollback and recovery
Documented with the commands in [MERGE_INTO_UNIFIED_DATABASE.md](../../data/csb-research/MERGE_INTO_UNIFIED_DATABASE.md) and tested by `run_rollback_validation.py` on a copy of the team database: a failed install or import commits nothing; `rollback.sql` drops the schema only after proving that nothing outside it depends on it (it refuses while a view, a foreign key or a column default outside the schema points into it) and afterwards the whole database equals the state before the install (DDL, owners, GRANTs, default ACLs, every row of every table); `catalog_csb` can be restored alone from `pg_dump -n catalog_csb`; the whole database can be restored from the pre-install backup. A bare `DROP SCHEMA ... CASCADE` is not the documented procedure, because it silently takes any dependent with it.

## Consequences
- Installing it into `registration_unified_spring2027` is purely additive and needs no privilege beyond what `catalog_owner` already has.
- Two places now hold course data (`catalog_research` for Account 1's courses, `catalog_csb` for CSB's). `catalog_csb.course_coverage` (optional views) says, per course, where it lives. Merging them is the staged route above.
- `catalog_csb.import_csb` is a replace-all importer for its own schema; the per-term history is `import_run`.

## Not decided here
Whether and when to take the route above; how a lab shared across lectures should be represented in the engine's model; whether the unified database should one day hold one section model instead of two.
