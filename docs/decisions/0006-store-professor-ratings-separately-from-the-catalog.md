# ADR-0006: Store instructors and Rate My Professors ratings in a separate schema (`professor_ratings`)

- **Status:** Proposed. Implemented in [data/professor-ratings](../../data/professor-ratings/README.md) (2026-10-17) and installed in the team database `registration_unified_spring2027` with the project owner's approval, after a backup; readable by the team's read-only role only, not pushed. It changes no shared interface (the backend does not read it).
- **Scope:** a new additive schema `professor_ratings` (V1-V5: instructors, RMP aggregates and individual ratings, app ratings and comments, term predictions); no change to `catalog_api`, `catalog_promoted`, `catalog_live`, `catalog_research`, `banner_evidence`, `cse007_snapshot`, the backend or the engine.

## Problem
Students choose sections partly by instructor, and Rate My Professors (RMP) is where they look. The catalog database deliberately holds no instructor names (`catalog_research` never imports them, because redistributing names from an authenticated Banner session was not verified), so there is nothing to attach a rating to. Two project-owner decisions of 2026-10-17 now change that, and both carry risk that this ADR records instead of hiding.

## Decision
1. **Ratings are opinion, not catalog facts.** They live in their own schema, carry the evidence level `RMP_STUDENT_OPINION`, and are never read by eligibility, tiers, approvals, promotion, `catalog_live` or the solver. A structure check proves that no object outside `professor_ratings` depends on it and no foreign key crosses its boundary.
2. **Instructor names are stored here, and only here.** *Decision of the project owner, 2026-10-17: reverse the earlier policy and import every Banner instructor name.* The names come from the local Banner research inputs. `catalog_research` keeps its rule (no names); the database is private to the team's tailnet, and no repository file contains a real name (tests use synthetic names). **Open risk:** whether Lehigh's terms permit redistributing instructor names collected from an authenticated Banner session is still unverified. Do not export this schema, publish a dump, or expose it through a public endpoint until that is settled.
3. **RMP is fetched automatically, at low volume.** *Decision of the project owner, 2026-10-17.* RMP has no official public API and its terms restrict automated access. The fetcher uses the unofficial GraphQL endpoint the RMP website itself uses, asks for aggregates for the roster (average rating, average difficulty, would-take-again percent, number of ratings) and, for semester trends, each rating's id, posting date, clarity/helpfulness/difficulty scores, would-take-again answer, course label and online flag, never the comment, tags, grade or anything else a student wrote. It reads one school's roster in about 14 paged requests, and the ratings of accepted matches only (about 46 requests), with a pause between requests and one request cap per run, stops on the first HTTP error or rate-limit answer, and keeps the raw response outside the repository. Only professors whose last name equals an instructor's are stored. **Open risk:** the endpoint can change or be blocked without notice, and use may breach RMP's terms; the owner accepted this for the hackathon. A hand-collected file or our own ratings are the fallbacks.
4. **A name match is a guess; only an exact, unique name is trusted.** The database applies the rules (`propose_matches`): exactly one RMP professor with the same folded last name and the same first name (more than one letter) and no other candidate is `AUTO_ACCEPTED`; no candidate is `NO_MATCH`; everything else, including a nickname or two professors with one name, is `NEEDS_REVIEW` and carries no rating until a person confirms it. A person's decision is never overwritten. The view `accepted_match_context` shows each accepted match beside the subjects the instructor teaches and the department RMP lists, so a different professor with the same name can be caught.
5. **Semester trends are approximate.** RMP records when a review was *posted*, not when the course was taken. `term_of_posting` maps a posting date to the semester it most likely describes (Jan 1-19: the previous fall; Jan 20-Jun 15: spring; Jun 16-Aug 24: summer; Aug 25-Dec 31: fall), in one function so the rule can change in one place. The trend views give per-semester and per-year averages with the change from the previous rated period, and `change_is_reliable` only when both periods have at least 3 ratings. Individual ratings are a cache of RMP: a fetch replaces a professor's ratings, so one RMP has removed disappears.
6. **Our own ratings accumulate next to RMP's.** *Request of the project owner, 2026-10-17.* `student_rating` stores a rating a student submits in the app: an opaque student id (never a name or e-mail), the professor, the semester the student chose, an optional course, quality and difficulty (1-5), would-take-again and an optional comment (up to 1,000 characters). One rating per student, professor, semester and course; a resubmission replaces it. The semester and year views count RMP and app ratings together with the count per source, so the trend keeps growing as the app is used. A moderator can hide a comment (scores still count) or remove a rating (counts nowhere). Basic structure only: no endpoint or UI uses it yet; a backend role would get `EXECUTE` on `submit_student_rating` alone. **RMP comments are not stored**: showing them would copy text the reviewers wrote on RMP, a separate decision.
7. **Predictions for a coming term are estimates, stored with their evidence.** *Request of the project owner, 2026-10-17: predict Spring 2027 quality and difficulty to show per course.* `predict_ratings.py` uses a recency-weighted mean of earlier ratings (RMP and app), optionally pulled toward the overall mean, with a per-course adjustment when students named the course. Its parameters are chosen by a backtest that predicts each past semester from earlier semesters only, and the result is stored as an immutable run with method, parameters, backtest and input hash, so a shown number can be traced and reproduced. Instructors without earlier ratings get no prediction. Every prediction carries a confidence; the UI must label it as predicted. Like ratings, predictions never affect eligibility, tiers or the solver.
8. **Honest sample sizes.** Every rating carries `sample_note` (`NO_RATINGS`, `LOW_SAMPLE` below 5 ratings, `OK`; per semester, below 3), and an unrated instructor still appears with a match status instead of a made-up number. These are informational: every rating is kept and counted.
9. **Append-only history.** Runs, rating observations and match decisions cannot be updated, deleted or truncated; the current state is the latest row. Writers are owner-only functions; the read-only role sees two views and no base table.

## Consequences
- Easier: a future "Professors" tab can read `professor_overview`, `instructor_term_rating` and `professor_comment` without touching the catalog. Nothing here changes what is schedulable.
- Harder: the backend allow-list does not include this schema, so exposing ratings needs a separate reviewed change (and the privacy decision in point 2).
- Follow-up: a person reviews the `review_queue` and every `accepted_match_context` row whose RMP department does not fit the subjects taught; the 60 non-CSE sections whose only instructor is "Staff" stay unrated by design.
